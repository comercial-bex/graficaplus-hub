# Project architecture rules

- Theme roles belong in `src/styles.css`; shared and feature components consume semantic tokens so light and dark modes remain consistent.
- CRM screens read persisted lead types through a narrow, RLS-scoped supplemental query with fallback only for a missing type column; this preserves existing RPCs and explicit WhatsApp projections before schema approval.
- The application sidebar always uses the dark sidebar token set, independently of the selected content theme, because navigation must keep its established identity.
- Contextual help copy is centralized in `src/lib/dicas.ts`, while shared tooltip behavior lives in `src/components/bex/Dica.tsx`, so explanations remain consistent across mouse, keyboard, and touch.
- The official Bex Print logo for white backgrounds is `public/marca/bex-print-fundo-claro.png` (`LOGO_FUNDO_CLARO` in `src/lib/marca.ts`): use it on every Bex Print PDF and on white surfaces the client sees, always on a white plate; never on dark backgrounds (black letters), and never on partner documents, which carry the partner's own brand.
- The logo for dark backgrounds is `public/marca/bex-print-fundo-escuro.png` (`LOGO_FUNDO_ESCURO` in `src/lib/marca.ts`, white letters): it is the one in the sidebar; never on white surfaces.
- WhatsApp inbox write actions (assign, transfer, status, notes, links, file replies, reprocessing) go through server functions in `src/lib/api/whatsapp-caixa.functions.ts` that check the caller's permission and then call SECURITY DEFINER SQL functions executable only by service_role, so the browser can never call those writers directly.
- Exception to the rule above: the PDF of a quote, work order or 3D quote goes to the client only through `enviarDocumentoAoCliente` in `src/lib/api/documento-whatsapp.functions.ts` (and the wa.me and copied-link records through `registrarEnvioPorFora` in the same file). Same lock: the server checks the caller's permission, then calls SECURITY DEFINER SQL functions executable only by service_role (`whatsapp_responder_arquivo`, `registrar_envio_documento`, `confirmar_envio_documento`, `arquivo_do_pdf_gerado`); every send is recorded in `documentos_enviados`, and nothing goes to a client without a person pressing the button. A quote moves from draft to sent only after the message left the queue (`confirmar_envio_documento`). `orcamentos.enviado_em` has known writers besides it: the manual status Select in `orcamentos.$id.tsx`, `camposDaRenovacao` in `orcamentos.index.tsx` and the `api_executar` SQL function.
- `ferramentas/` holds third-party material (e.g. `ferramentas/aiox-core`) stored for later use: it is not part of the app, is excluded from lint/typecheck/tests, and the instructions inside it (including its own AGENTS.md) do not apply to this system.
- AIOX execution must remain in an isolated external tooling environment; only reviewed planning documents enter `docs/planejamento-aiox/`, so installers, hooks and host configuration cannot change the application automatically.
- The partner order credit cap is decided by `parceiro_enviar_pedido` on the server; `src/domain/parceiros/credito-de-entrada.ts` only mirrors it for display, and partner screens treat a missing `entrada`/`atendente_padrao_id` from the database as "feature off", because the SQL is applied by hand after the code ships.
