# Project architecture rules

- Theme roles belong in `src/styles.css`; shared and feature components consume semantic tokens so light and dark modes remain consistent.
- CRM screens read persisted lead types through a narrow, RLS-scoped supplemental query with fallback only for a missing type column; this preserves existing RPCs and explicit WhatsApp projections before schema approval.
- The application sidebar always uses the dark sidebar token set, independently of the selected content theme, because navigation must keep its established identity.
- Contextual help copy is centralized in `src/lib/dicas.ts`, while shared tooltip behavior lives in `src/components/bex/Dica.tsx`, so explanations remain consistent across mouse, keyboard, and touch.
- The official Bex Print logo for white backgrounds is `public/marca/bex-print-fundo-claro.png` (`LOGO_FUNDO_CLARO` in `src/lib/marca.ts`): use it on every Bex Print PDF and on white surfaces the client sees, always on a white plate; never on dark backgrounds (black letters), and never on partner documents, which carry the partner's own brand.
- The logo for dark backgrounds is `public/marca/bex-print-fundo-escuro.png` (`LOGO_FUNDO_ESCURO` in `src/lib/marca.ts`, white letters): it is the one in the sidebar; never on white surfaces.
- WhatsApp inbox write actions (assign, transfer, status, notes, links, file replies, reprocessing) go through server functions in `src/lib/api/whatsapp-caixa.functions.ts` that check the caller's permission and then call SECURITY DEFINER SQL functions executable only by service_role, so the browser can never call those writers directly.
- Exception to the rule above: the PDF of a quote, work order or 3D quote goes to the client only through `enviarDocumentoAoCliente` in `src/lib/api/documento-whatsapp.functions.ts` (and the wa.me and copied-link records through `registrarEnvioPorFora` in the same file). Same lock: the server checks the caller's permission, then calls SECURITY DEFINER SQL functions executable only by service_role (`whatsapp_responder_arquivo`, `registrar_envio_documento`, `confirmar_envio_documento`, `arquivo_do_pdf_gerado`); every send is recorded in `documentos_enviados`, and nothing goes to a client without a person pressing the button. A quote moves from draft to sent only after the message left the queue (`confirmar_envio_documento`). `orcamentos.enviado_em` has known writers besides it: `renovar_orcamento_vencido` (SQL function from migration 20261117190000, called by `AcoesDoStatus` and by the renewal in `orcamentos.index.tsx`; the screens never write status or `enviado_em` directly, and a missing function shows a plain message instead of falling back to an UPDATE) and the `api_executar` SQL function. The staff screen no longer has a status Select: approve goes through `aprovar_orcamento`, and refusing or expiring is an UPDATE guarded by `.eq('status','enviado')`; the client's answer on the public link goes only through `responder_orcamento_publico`.
- `ferramentas/` holds third-party material (e.g. `ferramentas/aiox-core`) stored for later use: it is not part of the app, is excluded from lint/typecheck/tests, and the instructions inside it (including its own AGENTS.md) do not apply to this system.
- AIOX execution must remain in an isolated external tooling environment; only reviewed planning documents enter `docs/planejamento-aiox/`, so installers, hooks and host configuration cannot change the application automatically.
- The partner order credit cap is decided by `parceiro_enviar_pedido` on the server; `src/domain/parceiros/credito-de-entrada.ts` only mirrors it for display, and partner screens treat a missing `entrada`/`atendente_padrao_id` as "feature off" to support environments without the package migrations.
- The always-attended partner proposal uses one staged SQL source in `supabase/migrations/20261115160000_parceiro_sempre_atendido.sql`, mirrored in its review document; keep live normalized-body hashes and commented undo definitions together so review never implies application.
- Partner broadcasts use permission-checked authenticated SQL RPCs and the existing notification queue; missing-package reads return unavailable, never a fabricated audience, so preview cannot send before schema activation.
- Partner follow-up reminders (team 'sem contato' list and credit-expiry message) are decided in SQL (`_parceiros_sem_contato`, cron jobs) and mirrored in `src/domain/parceiros/sem-contato.ts` only for display and tests; a human team message is an outgoing message with origem 'humano' and enviada_por set, or origem 'celular'.
- Accounts payable writes go through SECURITY DEFINER SQL functions from migrations 20261116160000, 20261116170000 and 20261116210000 (all applied 16/11/2026) (`pagar_conta_pagar`, `estornar_conta_pagar`, `anexar_arquivo_conta_pagar`, `remover_anexo_conta_pagar`), called only from `src/components/financeiro/contas-a-pagar/use-conta-a-pagar.ts`; the list's 'Pagar' button only opens the confirmation dialog, and the payment's cash movement uses the informed payment date. Paying and attaching require financeiro.read in addition to the payment keys, because the vendedor role holds pagamentos.confirm/create without seeing finance; reversal and attachment removal are admin-only by role; BEFORE triggers from migration 20261116190000 also refuse, for any logged-in non-admin, taking a payable out of 'paga', deleting a paid payable, and deleting or detaching (or changing value, type, realizado or origem of) a cash movement with origem 'conta_pagar', so undoing a payment outside `estornar_conta_pagar` is admin-only too (owner decision, 16/11/2026); the gestor keeps read-only finance (decision of 03/10). Attachments live in the private bucket `contas-pagar-anexos`, separate from `comprovantes` (which also serves the client portal), and `contas_pagar_historico` is written only by triggers and by `_negar_conta_pagar`. Since Fase 2A (20261116210000): a permission refusal inside those functions (and in `baixar_parcela_compromisso`, `quitar_parcelas_ate`, `anexar_comprovante_parcela`, which now also require financeiro.read) does not raise; it records a 'tentativa_negada' history row and returns `{negado: true, mensagem}`, so every caller must pass the RPC result through `recusaDoBanco` (`src/domain/financeiro/contas-a-pagar-anexos.ts`) and treat it as an error. Paying requires an origin: an active bank account, or the 'Dinheiro' form with a receipt attached beforehand; a parcel baixa that posts to the cash book requires the same.
- Utility bills (contas de consumo, migration 20261116220000): a consumer unit lives in `unidades_consumo` (create/edit only by admin or gestor role, enforced by RLS; no delete, deactivate instead) and each monthly bill is a regular `contas_pagar` row linked 1:1 by `faturas_consumo` (one per unit and competence, UNIQUE). Bills are created only through `lancar_fatura_consumo` (same gate as "Nova conta a pagar": admin, or financeiro.read and pagamentos.create) and their extra fields change only through `corrigir_dados_fatura_consumo`; paying, reversing, attachments, history and the Conferência tab are the accounts payable ones, unchanged. Do not use `compromissos` for utility bills (fixed-value contracts only, owner decision 16/11/2026).
- Order status guard (migration 20261117230000, applied: the trigger exists in the live database, conferred on 21/11/2026): trigger `tg_orcamento_transicao_de_status` on `orcamentos` only allows rascunho to enviado, enviado to aprovado, rejeitado or expirado, expirado to enviado (renew) and aprovado to convertido, otherwise error `OR001`; the table lives in `orcamento_transicao_permitida`, any new status writer must stay inside it, and `sync_orcamento_3d_para_funil` keeps the funnel status when the 3D status would break it (`docs/ensaio-orcamento-transicao-de-status.md`).
- Sheet materials (acrylic) cost and stock by USEFUL area, never the gross sheet (owner decision, 22/11/2026): the Terzian sheet is invoiced as 1030 × 2030 mm but sells 1,00 × 2,00 m, so a sheet yields 2,00 m² (`materiais.largura_util_m` × `comprimento_util_m`, migration 20261122100000). A purchase's `rende_do_material` for a sheet is the useful area; `rendeSugerido` never suggests the gross size. The two `materiais_*` views must be recreated WITH their options (`security_invoker = true` on the operational one; `security_invoker = false, security_barrier = true` on the financial one), and a new column needs `GRANT SELECT (col) ON materiais TO authenticated` before recreating the operational view.
- Acrylic trophy quote (owner request 22/11/2026): the price is `custo cheio × multiplicador` (×3, with a quantity ladder of ×3, ×2,7, ×2,4 and a ×2,2 floor; ×3,5 for the exclusive premium; ×4 only for rush), computed by the pure function `calcularTrofeu` in `src/domain/trofeus/conta.ts`; tables `trofeu_regras` (one row; readable only with `financeiro.read`), `trofeu_modelos` and `trofeu_pecas` (migrations 20261122200000 and 20261122300000, read by any staff, written by admin or gestor, nothing for `anon`). The price reaches the browser only through the server function `cotarTrofeu` (`src/lib/api/trofeus.functions.ts`, rates assembled in `src/domain/trofeus/cotacao.ts` from `custos_tabela`, `custos_mao_de_obra`, `maquinas` and `COALESCE(custo_medio, custo_unitario)` of the materials, like `custo_cheio_do_produto`): the seller gets price and warnings only, `financeiro.read` also gets the breakdown; the public answer is built from an explicit field list. The trophy and its art reach a quote only through `salvarTrofeuNoOrcamento` and the RPC `salvar_trofeu_no_orcamento` (migration 20261122400000; closed to `anon` and `public`, `authenticated` checks `orcamentos.create` inside): the server recomputes the price, the browser sends only its choices and, at most, the total it saw (compared, never stored), and the lines are `orcamento_itens` with `origem_calculo` `trofeu` and `trofeu_arte` (the art is linked by `parametros.trofeu_item_id`, never by `gerado_por_item_id`, which belongs to the answers that charge). The trophy screen (`src/components/trofeus/calculadora-de-trofeu.tsx`, button "Troféu" in the quote and route `/orcamento-trofeu-novo`) never computes a price or reads a cost: it asks `cotarTrofeu`. The hand-picked multiplier (`multiplicadorManual`) is accepted only from `financeiro.read`, a multiplier below the floor only from gestor or admin (checked again on the server and logged in `logs_auditoria`, action `trofeu_multiplicador_manual`), and a trophy saved with an adjusted price can be edited only by someone who sees cost. Missing stock only WARNS (owner decision, 22/11/2026): a trophy can be quoted without the sheet. Every art line keeps a cost above zero, because `converter_orcamento_em_os` refuses a free item without cost; `remover_trofeu_do_orcamento` takes the trophy and its art out together. A missing rate is an error in Portuguese, never a made-up number. `trofeu_regras.id` must stay a uuid: `tg_auditar` casts `id` to uuid. The laser cuts acrylic up to 10 mm (owner; the manufacturer sheet says 30 mm) and the conta refuses a thicker piece. The DTF UV printer stays inactive and trophy decoration in DTF UV is an outside purchase until the machine exists with a cost. Whatever is still an estimate is listed in `trofeu_regras.provisorios` and `trofeu_modelos.provisorio`, and the screen must warn about it (laser speeds are researched, not measured).
